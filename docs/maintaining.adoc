= Maintain and release

This chapter is for a maintainer: what each workflow shows, how the tooling is
updated, and how a release is made. The repository follows the
https://lukewilliamboswell.github.io/roc-automation/[roc-automation manual],
which gives the reasons behind each practice.

== What each workflow shows

[cols="1,2,3",options="header"]
|===
| Workflow | Runs on | What it shows

| `release.yml`
| Manual dispatch; pull requests as a dry run
| The working tree passes the `check` task and its examples on the latest nightly, and the exact bundle, examples archive, documentation and SBOM sidecars proposed for publication work

| `nightly.yml`
| Daily
| The latest release's examples archive still works on the latest nightly

| `docs.yml`
| Pull requests, pushes to `main`, published releases
| The manual and site build; `main` and a final release deploy them
|===

`release.yml` is a thin caller of roc-automation's shared
https://lukewilliamboswell.github.io/roc-automation/workflows.html#the-shared-release-workflow-for-a-pure-package[release workflow]
at a full commit SHA. The shared workflow owns the jobs; this repository owns
its package, examples, `tests/spec.json`, notes and the tasks the workflow
calls from `Blueprint.roc`: `check`, `prepare-sbom`, `install-snippet` and `docs-path`.
The required status checks are `Release / Build and test the source`,
`Release / Test the release candidate`, `Validate source SBOMs` and
`Build the manual and site`.
The pull-request SBOM job independently validates the SPDX 2.3 schema and
checks the supplier-import regression fixtures. The shared workflow checks
sidecar bindings before publication.

The release workflow installs roc-blueprint with roc-automation's shared
installer, which selects the Blueprint release from the platform URL in
`Blueprint.roc`, and runs those tasks from `Blueprint.roc` without Nix. The
documentation and SBOM jobs use Kai instead: the local setup action
`.github/actions/setup-kai` installs Nix and Kai 0.0.11, restores Kai's
download cache (`~/.cache/kai`, keyed by job and lock) and runs `kai check`.
The `roc-stable` script compiler stays pinned, and the package nightly floats.

SBOM generation uses roc-automation's shared `sbom-sidecars` action. The
`prepare-sbom` task checks the bundle against the committed source and writes
the reviewed composition, and the committed `sbom/imports.json` records the
suppliers' SBOMs; the shared action owns generation and binding.

In the release workflow, downloaded utilities and compiler archives use
Blueprint's verified artifact cache, keyed by workflow, job, Blueprint release
and lock. Extracted trees are recreated and verified, while Roc package sources
have a separate cache. A cold job downloads the locked utilities; a warm job
restores and verifies them. Changing the lock invalidates the corresponding
cache key. The floating nightly may still need a fresh download when its
version changes.

The documentation jobs use `blueprint-tool`, with `kai` as its binary, to
resolve `docs-path` to the verified renderer in the store. CI reports
executable digest and bytes,
provisioning duration, native rendering time and peak RSS, output file sizes,
and separate preparation and API generation timings. Rendering uses a
precompiled Roc binary. The site's HTML,
PDF, Markdown and `llms.txt` come from the same AsciiDoc sources.

`nightly.yml` calls roc-automation's pinned published-release workflow. It
needs the canonical suite in a release's examples archive; the workflow has
nothing to test until a release made by `release.yml` is published. Successful compiler diagnostics are
retained; incomplete or failed setup cannot be reported as a compatibility
pass. Exact release and nightly overrides provide read-only diagnostic reruns.

== Update the tooling

Nothing updates the tooling automatically. Each of these is a pull request.

Refresh the lock:: Run `kai update` and commit `.kai/lock.json`. Run
`blueprint update` and commit `Blueprint.lock` for the release workflow.
Change the tooling compiler:: Change the tag in `Alias("roc-stable", ...)` in
`Kaifile.roc`, in `Fetch("roc-stable", Recipes.roc_nightly(...))` in
`Blueprint.roc` and in the `roc` field of every script to the same nightly.
The check fails until the scripts and `Blueprint.roc` agree. The roc-overlay
revision in `.kai/lock.json` must record that nightly: run `kai update roc`,
then `blueprint update roc-stable`, and fix any script the new compiler breaks.
Move the package compiler:: Run `kai update roc` to move `roc` to the latest
nightly roc-overlay records.
Upgrade Kai:: Change the platform and std URLs at the top of `Kaifile.roc` to
the new release's, as `kai init` writes them, and the version in
`.github/actions/setup-kai/action.yml`.
Upgrade Blueprint:: Change the platform URL at the top of `Blueprint.roc`.
The shared release workflow installs it with its own setup action, so a
roc-automation revision that records that release's checksums is needed.
Upgrade roc-automation:: Move every `lukewilliamboswell/roc-automation` reference
in `.github/` to the same reviewed full SHA, and the `roc-docs` and
`release-package` releases in `Kaifile.roc` and `Blueprint.roc` to the matching
`tools-*` tag, with the SHA-256s each release's `sha256sums.txt` publishes in
`Kaifile.roc`. Run `kai update` and `blueprint update roc-docs release-package`
and compare each declared system's SHA-256 with the release's
`sha256sums.txt`. The downstream dashboard reports a repository as current only when
every reference matches roc-automation's `main`.
Run `blueprint update` and review `blueprint lock show --json` (format 2)
as well as the lock diffs.
Update a package dependency:: Change its URL in the header of
`package/main.roc`, in its `Source` in `Kaifile.roc` and in its `SourceFile` in
`Blueprint.roc`, with the SHA-256 the supplier's release publishes for the
file, and its `version` in `sbom/package.json`. Run `kai update` and
`blueprint update`. Then delete `sbom/imports.json`
and regenerate it with roc-automation's `fetch-dependency-sboms` action at the
revision `release.yml` pins, as that workflow's composition step describes, and
review the supplier documents it records. If the supplier publishes no SBOM,
give the component an `unavailable_sboms` entry with the reason instead.
`kai run check` fails until the header and `Blueprint.lock` agree, and the release
dry run fails until the imports match what the suppliers publish.
Update a script dependency:: Change its URL in every script header, in its
`Source` in `Kaifile.roc` and under `RocPackages` in `Blueprint.roc`, and run
`kai update`.

== Make a release

. Choose the version. `roc bump` compares the package with the latest release
  and says how far the version must move:
+
[source,sh]
----
roc bump --old <latest release bundle URL> package/main.roc
----
. Write the notes in `docs/releases/<version>.adoc`, register them in the release-input manifest
  `docs/releases.adoc`, and merge that pull request. Write them for someone
  deciding whether and how to upgrade. Use `+{package-url}+` wherever the
  release's bundle URL belongs.
. Dispatch the *Release* workflow from `main` with that version.

The workflow then:

. Runs the `check` task with Blueprint, then rejects a version that already exists, one
  with no notes, and one that `roc bump --expect` says understates the change.
. Runs the examples against the working tree and compares them with
  `tests/spec.json`.
. Builds the bundle, the examples archive, the documentation archive, the SBOM
  sidecars and this manual as a PDF, and renders the notes with the real
  bundle URL and the `roc` it used. That record replaces a header pin as the
  statement of what the release was built and tested with.
. Tests the examples archive, unchanged, against the bundle, in a read-only job that checks out this repository to provision the locked
  utility and runs the examples from the archive.
. Publishes. A separate job, which checks out nothing from this repository and
  runs none of its code, attests the tested files, creates a draft release at
  the tested commit, uploads every asset, downloads each back and compares it
  with the tested file, and only then publishes.
. `docs.yml` then rebuilds and deploys the site, unless the version is a
  release candidate.

A release holds:

`<hash>.tar.zst`:: The package bundle. Its name is its content hash.
`weaver-examples-<version>.zip`:: The examples, depending on this bundle, with their recorded output.
`weaver-docs-<version>.zip`:: The API reference for this version, which the site restores.
`weaver-<version>.pdf`:: This manual.
Source-bundle SBOMs:: The bundle's `.spdx.json`, `.spdx-2.3.json` and `.cdx.json` sidecars describe it in SPDX 3, SPDX 2.3 and CycloneDX. Its `.sbom-manifest.json` binds those documents to the bundle.
`LICENSE`:: The UPL-1.0 terms, with the MIT notice of the upstream project weaver was forked from.

Build provenance for every asset is an attestation GitHub stores for the
repository, not a release asset: `gh attestation verify <file> --repo
lukewilliamboswell/weaver` checks a downloaded file against it.

No follow-up pull request is needed, because nothing on `main` names its own
release. A published release is never changed: if one is wrong, publish a new
version.

On a pull request the workflow builds and tests the same things under the
version `0.0.1-dryrun`, renders the newest notes, and publishes nothing.

A release candidate, such as `<version>-rc1`, goes through the same workflow. It
is marked as a prerelease, is never the latest release, and needs its own
notes file.

== How the site is put together

The site is this manual, rendered by the shared build-docs action, with the
API reference added beside it by `kai run site`:

* `main/` holds fresh API documentation for the working tree.
* Each release's API documentation sits under its version, such as `<version>/`,
  restored from the archive that release attached. Its address keeps working
  without its HTML being stored in Git, and generated documentation is never
  committed.

The manual leads with the latest release: its first program, its API reference
and its examples archive. Those parts are written by
`kai run install-snippet` before the manual is rendered, because a bundle
URL holds a hash nobody can write by hand.

`docs.yml` builds the site on every pull request and deploys it from `main`
and after a final release is published, since a release changes which one is
the latest.
