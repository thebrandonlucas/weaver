= Contribute

This chapter is for someone changing weaver: what to install, how to run the
checks a pull request must pass, and where each kind of test lives.

Use https://github.com/lukewilliamboswell/weaver/issues[issues] for bugs and
design discussion, and pull requests for changes. Say what behaviour changes
and how you checked it. A bug fix or a new behaviour comes with a test.

== Set up

You need three things:

* The `kai` command from https://github.com/thebrandonlucas/kai[Kai], at the
  release named by the platform URL at the top of `Kaifile.roc`. Its install
  script checks the download against the release's `SHA256SUMS`.
* A current Roc https://github.com/roc-lang/nightlies/releases[nightly] on your
  `PATH` as `roc`.
* The host tools listed in `Expect` in `Kaifile.roc`: `chmod`, `gh`, `git`,
  `gzip`, `realpath`, `sh`, `shasum`, `tar`, `test`, `touch`, `unzip` and `zip`.

Nix is not needed. The file and archive tools supplied by Linux and macOS
work; GNU coreutils is not required. Install GitHub CLI (`gh`) separately.
Kai downloads the pinned tooling compiler and its Roc packages on first
use, and checks each against `.kai/lock.json`. Run `kai update` after changing
its declarations, and commit the lock file. A checkout already has the lock it needs.

== Two compilers

[cols="1,2,3",options="header"]
|===
| Command | Chosen by | Used for

| `roc`
| You: the latest nightly
| Checking, testing, bundling and running the package and its examples

| `roc-stable`
| The release named in `Kaifile.roc`
| Running the scripts under `scripts/`
|===

The package is always tested with the newest compiler, because that is what its
users install. `roc-stable` exists so the repository's own tooling keeps
working on the day a nightly breaks something. It never checks or builds the
package, and it only exists inside `kai run` and `kai shell`.

Nothing pins a compiler for the package or the examples. Each script names
`roc-stable`'s release in its `roc` header field, so that running one with a
different compiler says why it misbehaves.

Kai's sbom plugin, named at the top of `Kaifile.roc`, writes and checks the
SBOM sidecars. `kai run prepare-sbom` checks the source and prepares the
reviewed composition. The release workflow uses roc-automation's shared
`sbom-sidecars` action to generate and check the sidecars; `kai sbom` runs
the same steps locally, and `kai sbom inputs` lists the inputs the
composition disposes of.

The sbom plugin normalizes the existing v1 composition when inspecting it and
binds fresh v2 sidecars. Missing component kinds remain `unknown`, missing
attribution and copyright remain `NOASSERTION`, and source references remain
empty. Legacy coverage keeps its reasons and statuses without acquiring a
component or aspect, so it makes no standard completeness claim. Keep the
reviewed composition and original supplier documents intact; changing a
profile label does not establish these facts. The source-import regression
checks the generated source and native inventories and rejects altered
supplier digests, subject identities and target labels.

== Run the checks

[source,sh]
----
kai run check      # source, scripts, fuzz corpus and site checks
kai run release-package -- test-examples  # recorded example output
kai workflow ci    # both of the above, in order
kai shell          # or enter the environment and run scripts directly
kai --help         # list every task
----

`kai run check` runs `scripts/check_all.roc`, which:

. Fails if a compiler pin appears outside `scripts/`, or a script's pin differs
  from `Kaifile.roc`.
. Checks that the package depends on exactly the bundles `Kaifile.roc` pins.
. Tests, checks and formats the scripts with `roc-stable`.
. Formats, checks and tests the package with `roc`.
. Builds each fuzz target and replays its committed corpus.
. Builds the API documentation site.

The examples, the bundle and the archives are checked by the shared release
workflow that `release.yml` calls, on every pull request: it runs every example
against the working tree and compares its output with `tests/spec.json`, then
bundles the package, builds the examples archive and runs the archived
examples, unchanged, against that bundle.

A pull request can fail because a new nightly arrived, with no fault in the
change. Compare with the latest run of the nightly workflow and with `main`
before treating a failure as yours.

== Where tests live

[cols="1,2,3",options="header"]
|===
| Kind | Where | How to add one

| Unit tests
| `expect` beside the code in `package/`
| Write an `expect` in the module. `roc test package/main.roc` runs them all.

| Example output
| `tests/spec.json`
| Add a case to the example's entry, then record its output; see <<change-an-example>>.

| Properties
| `fuzz/<name>/main.roc`
| A https://lukewilliamboswell.github.io/roc-fuzz/[roc-fuzz] target with a small `corpus/`; see <<search-for-inputs-nobody-thought-of>>.

| Script logic
| `expect` in the modules under `scripts/src/`
| Keep effects out of the module, and add it to the list in `check_scripts!`.
|===

== Change an example

An example's exact output is recorded, so a change to what it prints must be
recorded too:

[source,sh]
----
kai run release-package -- test-examples --update
----

Kai provisions the locked, released `release-package` utility used by
the shared release workflow. It tests with the `roc` on `PATH` and rewrites `tests/spec.json` from what the examples
print now. Review the diff like any other change. An example that cannot run for a reason outside
this repository is skipped in the specification with a `reason` and an `issue`
link; a skip without both is rejected.

Examples are for users of the package. Keep each one short, about one thing,
and commented for someone reading it with no other context. A test belongs in
`package/` or `tests/`, not in `examples/`.

== Search for inputs nobody thought of

Each target under `fuzz/` states a rule that must hold for every input, and
https://lukewilliamboswell.github.io/roc-fuzz/[roc-fuzz] searches for an input
that breaks it. The targets turn the fuzzer's bytes into a list of arguments,
some of them not valid UTF-8, and parse them as a command line would. Every
pull request only builds each target and replays its committed corpus. To
search, for a target `<name>`:

[source,sh]
----
roc build --fuzz fuzz/<name>/main.roc --output=<name>
./<name> run fuzz/<name>/corpus --time=60
----

When it finds a failure, fix the bug and keep the minimised input as an
ordinary `expect` in the package.

== Build this manual

Keep documentation focused on current reader tasks. Remove superseded guidance and status narratives; keep release changes in release records and investigations or unresolved work in issues. Follow the
https://lukewilliamboswell.github.io/roc-automation/documentation.html#write-project-documentation[shared documentation guide].

The manual is the AsciiDoc under `docs/`, one chapter per file, rendered by the
shared https://lukewilliamboswell.github.io/roc-automation/#build-docs[build-docs]
action. Every pull request builds it, and the site can be downloaded from the
`Documentation` workflow run. Kai provisions the locked native renderer
from the roc-automation release named in `Kaifile.roc`; no container or sibling checkout is needed:

[source,sh]
----
kai run install-snippet
kai run docs -- --docs-version main
kai run serve
----

The README's screenshot, `assets/pretty-errors.svg`, is the deploy
example's source and real output. Re-record it with `kai run capture`
whenever that example or its diagnostics change.

The first command writes the parts of the manual that depend on what has been
released into `docs/generated/`, which needs `gh` to be authenticated. The
second renders HTML and chapter Markdown into `.docs-out/site`, and the PDF
into `.docs-out/weaver.pdf`. The last adds the
API reference for `main` and serves the site on a free port, or the one named
by `SITE_PORT`; with `FETCH_RELEASE_DOCS=1` it also restores the API reference
of every release.
